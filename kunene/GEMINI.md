
# Implementation 

## Remote Execution (gRPC)

The `kunene.remote_actions` module enables executing actions on remote compute resources.

**Architecture:**
- **`ServerAction` / `NamedServerAction` (Remote)**: A gRPC server that accepts tasks, executes them in isolated temporary directories, and returns results. Supports `add_graph(name, graph, description)` for pre-registering workflows.
- **`RemoteAction` (Client)**: A wrapper that specifies a `target_action_name` to execute a pre-registered graph. Accepts `copy_paths` (list of local files or directories) to upload before execution. Files are sent by basename; directories are walked recursively with their internal structure preserved on the remote side.

**Protocol:**
- Defined in `kunene/protos/remote_actions.proto`.
- Supports bidirectional file transfer.
- Variable values and results are serialized as restricted JSON (`kunene/serialization.py`): dict/list/str/int/float/bool/None plus numeric numpy arrays (tagged, base64, dtype whitelisted on decode). Anything else raises `SerializationError`. Tuples decode as lists; numpy scalars decode as Python scalars.
- **Progress (`GetProgress` RPC)**: the client generates a `job_id` (uuid) and sends it in `ActionRequest`; the server registers `{job_id: tmp_dir}` while `RunAction` executes. Because `RunAction` is unary and blocks, the client's `_RemoteProgressPoller` (a daemon thread on a second channel) polls `GetProgress(job_id)` every `progress_interval` (default 2 s); the server returns the raw bytes of the shallowest `status.json` in the job's work directory. `_mirror_remote_status` reduces that to the RemoteAction's entry in the *local* status file: the fraction of the currently running remote action plus a message like `remote rad_solver: time 12.9 of 40`. The GUI keeps watching one local file tree and never learns about gRPC. Polling failures are ignored (RunAction reports hard failures); unknown job → `found=false`. Polling was chosen over a streaming RPC deliberately: a stream held open for hours dies with every network hiccup, polling is stateless.
- **Security Note**: Decoding a payload cannot execute code (pickle was replaced for this reason), but the gRPC channel is unencrypted and unauthenticated — use only within trusted networks.


## Design studies (`kunene/simulation_iterator.py`)

`SimulationIterator` and `JobIndex` live in this module (re-exported from `graph_actions`, which is where workflows import it from). They are one unit: the iterator writes the results directory, the index reads it.

`jobs_index.json` at a `SimulationIterator`'s results root maps job directories to the design points that produced them, so results can be retrieved by variable value and runs can be grouped without re-running anything.

- **Record**: `{job, groups[], variables{}, state, created_at, updated_at}`. Written by `SimulationIterator.solve` before the job runs (state `running`, so an interrupted run still leaves its design point and labels) and updated to `done`/`failed` after. Written atomically (temp + `os.replace`) like `status.json`; write failures are logged and swallowed — indexing must never break a workflow.
- **Cache, not authority**: `JobIndex.rebuild()` derives the whole index from the job directories (`iter_variables.json` for the variables, presence of `actions_output.pkl` for `done`), so result trees predating the index keep working; `load()` also adopts unindexed directories. Only group labels are unrecoverable — they exist nowhere else — so a rebuild preserves the labels of jobs it already knows.
- **Matching**: `values_match` compares numbers with `np.isclose` (a value that made a JSON round trip is not always bit-identical) and everything else with `==`; bools are kept off the numeric path so `True` does not match `1`. `find(where=...)` is a *partial* match (only the named variables are compared) and drives the query API; `find_exact` requires the same variable set and is what reuse uses — a job differing in an unmentioned variable is a different design point.
- **Directory names stay `job_N`**: encoding variable values in the name would have to invent a float format, would break when a study adds a variable, and could not express group membership at all. `JNAME` remains the (class-level) prefix.
- **Job numbering / restart**: `_allocate_job_path` always takes the next number from `JobIndex.next_job_number()` (max over index records *and* directories on disk, +1), so an existing results directory is added to rather than refused and a finished job is never written over. This replaced the old `run_iter`-based numbering and its "Results directory ... already exists. Restart is not yet supported" guard, which raised only when `job_0` existed — with `job_0` deleted it silently overwrote `job_1`. `run_iter` is now only the jobs-processed counter for progress reporting. `clean_start=True` (`rm_rundir`) is the way to start from an empty tree; it deletes the index with everything else, and group labels cannot be recovered by a rebuild.
- **Reuse** (`SimulationIterator(reuse_existing=True)`): `_reuse` returns a completed job's unpickled outputs instead of solving, adds the current call's labels to it, and makes it the `current_job` — but writes no run-level status of its own: it used to report `current_jobs=[]`, state `idle`, which inside a parallel batch claimed the batch was idle while its other jobs were still running. The caller reports instead (`solve` after the reuse branch, `solve_parallel` with the jobs actually running). Matching is `find_exact` (same variable set), so a job differing in an unmentioned variable is a different design point. A stale index entry (outputs deleted) falls back to running the job. Orthogonal to numbering: without the flag every design point given is run, appended after the existing jobs.
- **Parallel jobs** (`SimulationIterator(max_workers=N)`): `collect_for_expdes` fans the design points out over at most N child processes (`solve_parallel`), one per job; `solve` is one design point and always runs in the calling process. The split is the same one the graph's `asynch` mode makes: the parent stays the only allocator of job numbers and the only writer of `jobs_index.json` (`next_job_number` is a read-then-create, so allocating in a child would let two jobs claim `job_3`), while a child only runs `_run_job` in the directory handed to it. Results come back through `actions_output.pkl` rather than a pipe — the child writes it anyway, so nothing extra has to be picklable and the structure matches a serial run exactly. Failure semantics follow the serial sweep: the first failing job terminates its running siblings (`_abort_running_jobs`, marked `failed` in the index) and raises `AsyncActionError` with the child's traceback. `chdir` is why this is processes and not threads. A child's stdout/stderr are redirected into `job_N/job.log` (`_redirect_child_output`, at *fd* level via `dup2` so the solvers' subprocesses and pre-fork logging handlers follow, with a `sys.stdout`/`sys.stderr` rebind as fallback where those are not real descriptors — a notebook, pytest's capsys): a child inherits the terminal *and* the parent's open tqdm bars, and any stray write shifts a `position=`-held block that tqdm then repaints at the old offsets. `JOB_LOG_PATH` is in `PROTECTED_FROM_CLEANUP`. The child also drops the parent's tqdm instances (`_silence_inherited_bars`): a fork copies the live bars and tqdm's class-level registry, so anything the child sends through `tqdm.write` would redraw all of them into its log. On the parent side `_JobBar` holds `tqdm.contrib.logging.logging_redirect_tqdm` open for the life of the bars, so the parent's own log records go through `tqdm.write` instead of over them. `progress_bar` is threaded through `collect_for_expdes`/`collect_for_varrange`, so a sweep can ask for bars explicitly and not only get them by tty auto-detection. `_JobBar` wraps the optional tqdm bars (`kunene[progress]`): a batch bar counting jobs (position 0) plus one bar per running job (positions 1..n, `leave=False`, lowest free line reused as jobs come and go). The job bars are driven by *reading each job's own `status.json`* with a `StatusWatcher` — the parent has no other view into a forked child — refreshed from the wait loop every `BAR_POLL_INTERVAL` (0.3 s); `progress.job_fraction` averages the action states into the single number a bar needs (done actions count 1, running ones add their own fraction); the message names the running action and its place in the graph's action list, its own message, and its own percentage (`rad 1 of 3: time 80 of 100 (80%)`), so the bar's job-wide percentage cannot be misread as the solver's — and where an `asynch` graph has several running at once, it names them all instead (`3 of 5 running: rad_a (80%), rad_b (34%)`), which is what `DESC_WIDTH` (56) is sized for. The message goes in the *description*, padded to `DESC_WIDTH`, because tqdm hardcodes a leading `', '` on `{postfix}` (std.py:569). Bars are created only when tqdm imports *and* — for the default `progress_bar=None` — stderr is a tty, so a redirected run stays clean; every method no-ops otherwise. It is the terminal channel and is deliberately independent of `status.json`, which is written regardless. The start method comes from `util/parallel.get_context()` (see below), and the worker is the module-level `_run_job_in_child` rather than a closure, so it survives being pickled for `spawn`.
- **Numpy values**: `as_jsonable` coerces numpy scalars/arrays to plain Python for both the index and `iter_variables.json` — variable values commonly come from `np.arange`, whose items `json.dump` cannot serialize.

## Start methods (`kunene/util/parallel.py`)

`parallel.get_context()` is the single place that decides how kunene starts a child process: `fork` where the platform has it, `spawn` otherwise. Both `SimulationIterator.solve_parallel` and `WorkAction._observed_eval_async` call it. `START_METHOD` (module attribute) and `$KUNENE_START_METHOD` force a method and still fall back, so an unusable setting degrades to a working run rather than to an exception; `tests/test_parallel_start_method.py` uses that to run the Windows path on Linux.

Before this existed both call sites asked for `'fork'` and fell through to the platform default on Windows, where `Process.start()` then died pickling the closure they passed as `target` — so the `except ValueError` read like a portability fallback but was only a slower way to fail. Making `spawn` work needed three things:

- **Module-level workers.** `simulation_iterator._run_job_in_child` and `actions._async_eval_worker` replace the closures. What the closure captured (`self`, the shared error dict) is now passed as an argument, which costs nothing under `fork` — args are not pickled there — and is what makes `spawn` possible.
- **`__getstate__` where a live handle would travel.** `WorkAction.__getstate__` drops `_async_proc` (a `multiprocessing.Process`, unpicklable, and the parent's business anyway — it is joined and terminated there). `SimulationIterator.__getstate__` additionally drops `_status_reporter`: it owns the results-root `status.json`, which only the parent writes; a child reports through the reporter its own graph creates in the job directory. `StatusReporter.__getstate__`/`__setstate__` drop and rebuild `_lock`, `_hb_stop` and `_hb_thread` — a child never heartbeats and writes its sidecars without the lock, which is why `action_state` keys off `_owner_pid` and not off what it holds. `_owner_pid` is pickled, so a spawned child still recognises itself as a child and the sidecar mechanism is unchanged.
- **Observers stay.** They are not dropped: under `spawn` the child re-runs the graph, and its actions still have to notify their parent graph *inside that child*.

- **The script is not re-imported.** Stock `multiprocessing` has a spawned child re-import `__main__` (as `__mp_main__`) so that objects pickled by reference to the script resolve — which makes the child run the script's top-level code again, and a script that starts the sweep at top level would start it again in every child (multiprocessing raises a RuntimeError about bootstrapping). kunene does not need the script in the child (the workers are its own module-level functions and the graph arrives as a pickle), so `parallel.start_process` and `parallel.start_manager` start every spawned child inside `parallel._hidden_main`, which sets `__main__.__spec__ = None` and removes `__main__.__file__` for the duration of `Process.start()`: `spawn.get_preparation_data` then sends neither `init_main_from_name` nor `init_main_from_path`, and the child imports nothing of the caller's. A module-level lock serialises this, since `__main__` is process-wide. The `Manager()` server is a spawned process too, hence `start_manager`. Both call sites go through these two functions; nothing else in kunene creates a `Process`.

What `spawn` then asks of the caller is only that the graph and its actions be picklable *without* the script: an action class (or function) defined in the calling script itself pickles as `__main__.X`, which the child cannot look up, and would die at unpickling with an `AttributeError` the parent only sees as an exit code. `parallel.main_references` (a `pickle.Pickler` whose `reducer_override` merely notes classes and functions with `__module__ == '__main__'`) runs over the arguments before the start, and `start_process` raises `SpawnError` naming them — move the class into an importable module (the examples keep theirs in `examples/example_actions.py`). `IMPORT_MAIN` / `KUNENE_SPAWN_IMPORTS_MAIN=1` opts back into multiprocessing's behaviour (script re-imported, so in-script classes work and the script must not start the sweep at top level). Documented on `max_workers`, on `asynch`, and in `docs/parallel.rst` (the *Running in parallel* chapter) under *Child processes and start methods*; `tests/test_parallel_start_method.py` runs a plain top-level script in a subprocess under forced `spawn`.

`_redirect_child_output` and `_silence_inherited_bars` still work under `spawn`, doing less: a spawned child inherits the console (so the fd-level `dup2` still matters, and the solvers it starts follow it) but neither the parent's tqdm registry nor its logging configuration.

## Progress reporting (`kunene/progress.py`)

Workflow progress crosses the process boundary (to a GUI) through `status.json` files in the work directories, never through in-process callbacks.

- **Writer**: `StatusReporter`. Writes atomically (temp file + `os.replace`) on every state change; a daemon heartbeat thread rewrites every `heartbeat_interval` (5 s) so `updated_at` distinguishes a slow run from a dead one. Write failures are logged and swallowed — reporting must never break a workflow. A per-process ownership registry (resolved path → *weak* reference to the owner, so an owner dropped without being finished does not hold its directory for the life of the process) makes a reporter for an already-owned directory a no-op, so a graph nested in another graph (same cwd) does not clobber the owner's file; the nested graph reports its actions through the owner's reporter instead. Caveat: a nested graph run as an *async* action lives in a child process with its own registry and would write the same file. `takeover=True` claims a directory anyway and `_displace()`s the previous owner (inactive, heartbeat stopped, file untouched) — for a new *run* of a study, where standing aside would mean reporting nothing; `finish` removes the registry entry only when it is still its own. `MultiReporter` forwards `action_state` and `fail_running` to several reporters at once (`active` if any of them is): it is what a graph inside a `WorkArea` reports to, filling both the work area's own file and the enclosing graph's. `mark_failed(path)` is the outside-in counterpart, for a file whose writing process was killed: run state `failed`, every `running` action `failed`, `pending` ones untouched (they never ran), terminal files left alone.
- **Pass-through containers**: the entries of a status file are the actions, not the containers holding them. `WorkAction._progress_names()` returns the names an action occupies (`[self.name]`) and `_progress_passthrough` says whether the enclosing graph sets a state for it; `DirectedGraph` and `WorkArea` override both, returning the flattened names of what is inside them. So `reporter.start()` registers the leaves in tree order — which is also what makes `job_fraction`'s *n of m* count them — and `DirectedGraph._report_action` skips a pass-through child. This is why a `WorkArea` around a solver no longer occupies a job's status file with an entry that has no fraction until the whole area is done; `WorkArea.solve` hands the graph inside it the reporter it was given (`DirectedGraph._report_to` then combines it with the graph's own through a `MultiReporter`), so the same states reach both files. A `SimulationIterator` is deliberately *not* pass-through — its jobs have directories and status files of their own — and reports `run_iter/jobs_total` into its single entry from `_report_status`; a `RemoteAction` likewise mirrors the remote graph into its own entry. A failure inside a pass-through container shows as the failed *action* plus the graph's `state: failed`; the container name itself is never written, so a failure in a work area's own setup (missing `copy_paths`) leaves its actions `pending` and only the graph state failed.
- **`DirectedGraph.solve`**: creates a reporter in the run directory (cwd at solve time, so `WorkArea`/`SimulationIterator` place it correctly), reports `pending`→`running`→`done`/`failed` per action, sweeps newly finished actions immediately after each synchronous eval (so sequential chains show correct states mid-run, not only at pass end), and marks completed actions `done` even when a later action fails. The former busy-wait now sleeps 50 ms when no action can start or finish.
- **`SimulationIterator.solve`**: one reporter at the results root for all jobs (`jobs_total`, `jobs_done`, `current_job`, `current_jobs`; state `running`/`idle`/`failed`/`done`). The counts are the *batch's*: `_start_batch` (called by `collect_for_expdes` and by `solve_parallel`) sets `jobs_total` and zeroes `run_iter`, so a second sweep of three reports 3 of 3 rather than 6 of 3, and it sets `_in_batch` so that the `solve()` calls a serial sweep makes leave those counts alone while a `solve()` of the caller's own clears `jobs_total` (one design point belongs to no batch). Every entry point ends with `_finish_status`, which writes the final state, stops the heartbeat and **releases the results root**: without it the directory stayed owned for the life of the process, so a second iterator on the same tree got an inactive reporter and reported nothing at all while the first one's heartbeat kept a stale file looking alive (`clean_start=True` re-runs left no root `status.json` whatsoever). `_report_status` recreates the reporter, so an iterator stays usable afterwards, and it creates it with `takeover=True` — a new run of a study owns its results root even where an older iterator object still holds a reporter for it; `rm_rundir` finishes first, since it is deleting the directory being reported into. On failure the parent reports `current_jobs=[]` and `_abort_running_jobs` stamps each terminated job's own `status.json` through `progress.mark_failed` — a killed process cannot report itself, and the file otherwise claimed to be running for ever while the index recorded it failed. `current_jobs` is the list of jobs running at this moment (several with `max_workers` > 1, empty between jobs); `current_job` names the last job started and is never cleared, so a reader following one job keeps showing its final state. Each job's own `status.json` is written by the process running it, so per-action progress needs no channel back to the parent.
- **Readers** (GUI side): `StatusWatcher.poll()` re-reads only when the file's `(mtime_ns, inode, size)` signature changes — inode, because coarse filesystem timestamps make rapid writes share an mtime, and `os.replace` gives a new inode per write. `RunWatcher.poll()` (non-blocking, for GUI timers) follows root + every job in `current_jobs` (falling back to `current_job`), returning `{root, job_name, job, jobs}` — `jobs` maps job directory to status, `job_name`/`job` are the first of them, kept for single-job readers; `format_status` prefixes each block with the job directory when more than one runs; `watch_run` is the blocking generator; `is_alive()` checks heartbeat staleness.
- **Solver percent-complete**: `progress.FileProgressTail` is a daemon thread started around the blocking `subprocess.run` (stopped in a `finally`, so no 'running' write can land after the done sweep). It polls the tail (last 64 KB) of the solver's redirected stdout every 2 s, parses the latest simulation time, and reports `fraction = (t - t_start)/(t_end - t_start)` (only when changed by ≥0.001) with a `message` like `time 12.9 of 40`. Parsers live in `kunene/util/solver_progress.py` (pure stdlib, calibrated against real output): OpenRadioss `NC=/T=` lines with the stop time from the `/RUN` card; LS-DYNA native `t ... dt` / `at time` lines *and* `NC=/T=` (deck-through-OpenRadioss wrapper) with ENDTIM from `*CONTROL_TERMINATION` in the *written* deck (post parameter substitution); OpenFOAM `Time = ...` log lines with `endTime`/`startTime` from `system/controlDict`. Unknown termination time or missing reporter → `start()` is a no-op; parse failures are swallowed (fraction stays `null`). The graph hands its effective reporter to each child via `node._progress_reporter` before eval; a nested graph forwards the owner's reporter, so nested solver fractions (and nested action states) reach the owning status file.
- **Fork safety (`asynch` mode)**: an asynch action runs `solve()` in a forked child holding a copy of the reporter. The child never writes `status.json` and never uses the inherited lock (which can be copied in a locked state): `action_state` detects the pid change and writes that one entry to a per-action sidecar (`.<action>.progress.json`, atomic). The owner merges sidecars into `status.json` on every write and heartbeat — so async fractions surface at heartbeat cadence (5 s default) — keeping state authority only for the actions it *drives* itself (`_driven`, the names it has called `action_state` for: sidecar contributes fraction/message only while running; terminal → sidecar deleted) and adopting the rest wholesale, state included — the children of a nested async graph, and the actions of a pass-through container that ran in a child process, which `start()` registers here but which only that child ever sets a state for. (`_driven` replaced `_own_actions`, the set registered by `start()`, for exactly that case.) All sidecars are removed at `finish()`. `start`/`update`/`finish` are no-ops in a child.
- **GUI (optional)**: the top-level `kunene_gui/` package (separate from `kunene` so PySide6 is an optional `[gui]` extra) is a pure reader on this layer. `kunene_gui.RunProgressWidget` owns a `QTimer` that drives `RunWatcher.poll()` and renders the iterator job counter plus the current job's action progress bars; `kunene_gui.StatusView` is a passive renderer of one status dict for callers that manage their own polling. Run standalone with `python -m kunene_gui [results_dir]`.
- **Async failures**: the child of `_observed_eval_async` catches any exception from `solve()`, stores `type: message + traceback` in the shared result dict, and exits non-zero. The watcher thread classifies the outcome — stored error, non-zero exit code (segfault/oom-kill/terminate), or missing result — and notifies the graph with `[action, 'Failed']` instead of `'Done'`. `DirectedGraph.update` collects these in `self.failed`; the solve loop then marks the action `failed` in the status file (message = first line of the child's error), terminates the still-running sibling children (marked `failed` with a 'terminated: a sibling action failed' message), and raises `AsyncActionError` carrying the child's full traceback. Sync-mode failures propagate directly as before.
